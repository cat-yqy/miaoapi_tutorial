# 最佳实践：把 Codex 用成可靠的队友

Codex 的上限不只取决于模型，还取决于你给它的上下文、约束、验证方式和权限边界。下面这些原则，比任何“神级提示词”都更有用。

## 十条最重要的原则

### 1. 把它当队友，不是自动补全

给 Codex 一个目标、一点上下文和明确的完成标准，而不是只丢一句“帮我改一下”。你负责定义问题和验收，它负责执行和迭代。

### 2. 一个任务一个线程

不要用一个 thread 从项目初始化聊到三个月后。上下文会污染，早期信息会被压缩掉，模型越来越容易跑偏。任务分叉时用 `/fork`，不要把所有事情塞进同一个会话。

### 3. 复杂任务先计划

跨模块、需求模糊、风险高的任务，先用 `/plan`。计划阶段发现理解偏差，比写完三百行再返工便宜得多。

### 4. 把长期规则写进 `AGENTS.md`

构建命令、测试命令、代码风格、不能改的接口、PR 要求，都应该写进 `AGENTS.md`，而不是每次在提示词里重复。重复犯错两次，就更新它。

### 5. 让 Codex 能验证自己的改动

能跑测试就让它跑测试，能复现就让它先复现，有 lint/typecheck 就让它执行。没有验证的“看起来正确”，很容易在边界条件下崩掉。

### 6. 先收紧权限，再按需放开

默认使用工作区沙箱和按需审批。只有在你信任仓库、理解风险，或身处隔离环境时，才使用 Full Access。不要因为“少点几次确认”就永久全域放权。

### 7. 并行读，谨慎并行写

子代理适合探索、审查、日志分析、测试等读多写少的任务。多个 agent 同时改同一批文件，冲突和协调成本通常大于收益。需要并行写时，用 worktree 隔离。

### 8. 先固化流程，再自动化

流程还不稳定时，不要急着设定时任务。先在普通对话里跑通，再把步骤写成 Skill，最后才用 Automation 或 `exec` 定时执行。

### 9. 审查意见要自己判断

Codex 的 `/review` 很有用，但它不是最终裁决。逐条看文件、行号和触发条件；机械检查交给 CI；安全关键逻辑由人复核。

### 10. 不要用便利换掉安全

密钥、token、客户数据、内部地址，不要出现在提示词、截图、提交或 `AGENTS.md` 里。Web、MCP、插件、PR 文本都可能带来 prompt injection，外部内容一律当作不可信输入。

## 按任务难度选择工作方式

| 任务类型 | 建议方式 | 不要做什么 |
| --- | --- | --- |
| 文案、重命名、小修 | 直接做，低推理 | 为一行改动写长计划 |
| 单文件 bug | 先复现，再修，跑回归测试 | 没复现就凭猜测改 |
| 普通功能 | 简短计划 + 垂直切片 | 一次改十几个文件 |
| 跨模块重构 | `/plan` + `/goal` + worktree/Cloud | 没有回滚方案就大改 |
| 长任务 | Goal、后台任务、分阶段验收 | 一个提示词要求“全部做完” |
| 重复任务 | Skill + Automation | 流程没跑通就定时 |
| 高安全场景 | 只读/最小权限 + 人工复核 | Full Access + 自动合并 |

## 上下文管理

### 给对的上下文，而不是更多上下文

好的上下文包括：

- 相关文件和目录；
- 错误日志和复现步骤；
- 设计稿或接口文档；
- 现有实现和测试；
- 不能改的边界。

无关的打开文件、整份日志、历史聊天记录，往往会稀释注意力。IDE 的自动上下文很方便，但打开二十个标签页并不会让 Codex 更聪明。

### 重要信息不要只存在于对话里

对话会被压缩。把必须长期生效的内容放到：

- `AGENTS.md`；
- `README` / 架构文档；
- 任务描述文件；
- 测试和类型定义。

### 长任务要主动整理

- 上下文快满时用 `/compact`；
- 任务分叉时用 `/fork`；
- 只想问个问题时用 `/side`；
- 并行写操作时用 `/worktree`；
- 一个任务结束后用 `/new`，不要继续背着旧上下文。

## 验证闭环

一个可靠的循环至少包含：

1. **复现**：先让问题稳定出现；
2. **修改**：最小范围地改；
3. **验证**：跑测试、lint、类型检查、真实命令；
4. **审查**：`/diff` + `/review`；
5. **记录**：说明改了什么、为什么、怎么验证。

如果任务无法自动验证，就让 Codex 给出**人工验证步骤**，并明确哪些地方它不确定。

## 权限与安全

### 权限矩阵

| 场景 | 建议权限 |
| --- | --- |
| 读代码、调研、审查 | Read-only |
| 日常改代码 | Auto / `workspace-write` + `on-request` |
| 受信任仓库的重任务 | 可临时放宽，但保留可回滚点 |
| 隔离容器 / 一次性环境 | 才考虑 Full Access |
| 无人值守自动化 | 最小权限 + 独立 worktree + 可审计日志 |

### 外部内容的信任边界

以下内容都可能包含恶意指令：

- 网页搜索结果；
- MCP 工具返回的内容；
- 第三方插件；
- PR 描述、Issue、commit message；
- 你粘贴进来的日志和文档。

Codex 应该把这些当作**数据**，不是命令。你在设计自动化时，也要避免把不可信文本直接拼进高权限提示词。

### 密钥管理

- 不要把 API Key 写进仓库、配置样例、截图或 `AGENTS.md`；
- CI 中使用 secret，并尽量只对单次执行注入；
- 怀疑泄露就立即轮换，不要只删文件；
- 共享 `~/.codex` 前检查 memories、sessions 和 auth 文件。

## 并行与成本

### 什么时候值得并行

适合：

- 多个独立模块的只读分析；
- 安全、测试、可维护性多角度审查；
- 多个互不依赖的 bug；
- 云端长任务。

不适合：

- 多个 agent 改同一批文件；
- 强顺序依赖的迁移；
- 任务本身很小，协调成本高于收益。

### 成本控制

- 简单任务用低推理和快模型；
- 子代理会增加总 token；
- 图片生成会明显更快消耗额度；
- 长会话定期 `/compact`，任务结束 `/new`；
- 不要为了“更稳”无脑开最高推理；
- 用 `/usage` 和 `/status` 观察消耗。

**更贵的配置不一定更好。清晰的任务定义 + 合适的模型 + 验证，通常比最高推理更有效。**

## 团队落地

### 从一条真实工作流开始

不要一上来就配置所有 MCP、安装所有插件、给所有仓库开自动化。选一条团队真正重复的流程，例如：

- PR 审查；
- 发布说明；
- CI 失败排查；
- 新成员代码库导览。

先手动跑通，再固化。

### 团队资产分层

| 资产 | 放在哪里 | 作用 |
| --- | --- | --- |
| 项目规范 | 仓库 `AGENTS.md` | 构建、测试、风格、禁区 |
| 审查规则 | `AGENTS.md` 的 `## Code Review Rules` | 统一审查重点 |
| 可复用流程 | `.agents/skills` | 团队共享技能 |
| 外部工具 | MCP / Plugins | 文档、浏览器、Issue、监控 |
| 定时任务 | Automations | 重复巡检和汇总 |

### 度量效果，而不是感觉

可以观察：

- PR 从提交到合并的时间；
- review 发现的问题类型；
- CI 失败恢复时间；
- 重复劳动减少了多少；
- 返工和回滚是否增加。

如果 Codex 让 review 变多、diff 变大、返工变多，先检查任务拆分、`AGENTS.md` 和权限，而不是简单换更强模型。

## 常见反模式

| 反模式 | 后果 | 更好的做法 |
| --- | --- | --- |
| 一个 thread 干所有事 | 上下文污染、越来越笨 | 一个任务一个 thread |
| 提示词只有“优化一下” | 目标不清、反复返工 | 写清 Goal / Context / Constraints / Done |
| 不跑测试就接受 | 表面正确、边界崩溃 | 先复现，再验证 |
| 默认 Full Access | 误删、越权、供应链风险 | 最小权限，按需放开 |
| 两个 agent 改同一批文件 | 冲突、覆盖 | worktree 隔离，读写分离 |
| 流程没稳定就自动化 | 无人值守地重复犯错 | 先手动跑通，再 Skill，再 Automation |
| 把所有规则塞进提示词 | 上下文浪费、规则漂移 | 放进 `AGENTS.md` |
| 盲信 review 结论 | 漏掉真实风险 | 看证据、行号和触发条件 |
| 安装所有 MCP/插件 | 攻击面变大、工具选择困难 | 只接真实工作流需要的 |
| 用 Codex 替代思考 | 架构和取舍没人负责 | 人定义目标和验收，agent 执行 |

## 上线前检查清单

### 开始前

- [ ] 任务目标能用一句话说清；
- [ ] 相关文件和复现步骤已提供；
- [ ] 约束和“不要做什么”已写明；
- [ ] 完成标准可验证；
- [ ] 权限模式与风险匹配。

### 进行中

- [ ] 复杂任务先看计划；
- [ ] 改动范围没有失控；
- [ ] 测试/构建真的在跑；
- [ ] 失败路径和边界有覆盖；
- [ ] 没有密钥、日志、调试代码混入。

### 提交前

- [ ] `/diff` 看过；
- [ ] `/review` 跑过；
- [ ] 测试和 lint 通过；
- [ ] 文档/类型/配置同步更新；
- [ ] 需要人工确认的点已列出。
